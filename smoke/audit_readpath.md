# 读路径体检:库里"没有"的列,会不会在 Go 这层被摊平成空串

## 为什么需要它

「禁止空串表示 null」这条规则,**改 proto 只做到了第一段**。整条链是四段:

```
proto 加 optional  →  库列可为 NULL  →  Go 模型是指针  →  读路径指针直传
```

任何一段还在用裸类型,整条链就退回原样 —— **而且全程零报错**,
因为每一段单独看都是对的。gorm 把 NULL 扫成 `""`,再被 `proto.String()`
包成"存在且为空",客户端于是分不开"没有"和"是空的"。

## 怎么跑

```sh
python3 audit_readpath.py > /tmp/models.json   # 抓 gorm tag:表→列→Go 字段/类型
python3 gen_nullq.py                           # 生成计数 SQL(只看非指针的列)
mysql -N -B < /tmp/nullcheck.sql | awk -F'\t' '$3+0>0'
```

## ⛔ 这个筛法有个盲区,2026-08-29 就漏了最大的一处

上面按「**列可为 NULL 且真有 NULL 行**」筛。但一列如果**全是空串、一个 NULL 都没有**,
它照样是病 —— 而且是更重的病(说明写入侧从来没写过 NULL),却会被这个筛法整个跳过。

那次漏掉的是两张**主用户表**的头像:

| 列 | 总行 | NULL | 空串 |
|---|---|---|---|
| `hi_did.hi_user.avatar` | 528 | **0** | 498 |
| `hi_club.hi_chat_user.avatar` | 543 | **0** | 514 |

是端到端查 `hi.ai.Agent/List` 的回包、看见 27 个 `avatar: ""` 才顺藤摸回来的。

**所以两个方向都要看:**
1. `nulls > 0` —— 库里有 NULL 而 Go 是裸类型 → 读路径摊平;
2. `nulls = 0 且 empties > 0` —— 从来没写过 NULL → 写入侧也是空串语义。

**最后一道永远是端到端**:真调一次接口,数回包里有多少个 `"字段": ""`。
它不依赖任何静态假设,也不会被筛法的盲区骗过去。
